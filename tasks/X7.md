## Definition of "hard" (target band, pinned by tests)
- `par` between **25 and 34** (daily d7 = 30 was the previous max; h6 = 34 is the new ceiling)
- exactly **3 guards**, **1–2 cameras**, **0–1 laser**, `maxPauses` 3
- standard map: 8 columns × 12 rows, one S, one E, one L
- patrol / camera / laser periods must divide 24 (enforced by `npm run validate`)

## Task
Design 10 hard heists in `levels/hard/`, one per mechanic moment, in
increasing pressure (teach → practice → test across the set):
h1 laser timing · h2 camera + laser · h3 three guards crossing · h4 pause
chain · h5 corridor under sweep + laser · h6 very tight par · h7 loop +
pingpong combined · h8 double camera · h9 long route + laser · h10
"signature hard" (non-empty `moment`, still type `normal`).

Each `.lvl` follows the existing format (see levels/daily/d7.lvl): header
comment, `name`, `type: normal`, `moment`, `maxPauses`, `par`, ASCII `map`,
`guards` / `cameras` / `lasers`.

## Acceptance criteria
- `npm run validate` green: all 10 solvable, par matches the solver, periods divide 24; `levels/levels.json` regenerated and committed.
- `tests/unit/levels-hard.test.ts`: for each h1–h10 — parses, solver par == declared par, a winning plan exists (`run` → `won`), and the hard band holds (par 25–34, 3 guards, 1–2 cameras, 0–1 laser, maxPauses 3); plus the per-level moment pins (laser on the golden route, pairwise crossings, minPauses, corridor, par ≥ 33, loop+pingpong, 2 cameras, signature moment).
- `docs/design/hard-levels.md`: 10 rows × 4 fields (game intention, expected solution, failure modes, playtest criterion), HYPOTHESIS vs OBSERVED.
- Full local check green: `npm run typecheck && npm run lint && npm run test && npm run validate && npm run build`.
- The 10 levels appear in the /dev/viewer catalog (levels.json id `hard/hN`).
